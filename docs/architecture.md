# How the site works

The mechanisms behind the page, for whoever changes it. The map of files is in the [README](../README.md#structure).

- **The URL decides the language.** `[lang]/+layout.svelte` sets the `locale` store from the route before anything renders, so the prerendered `/ru/` is Russian; the header's EN/RU are plain links and remember the choice for `/`. Strings live in `src/lib/shared/i18n/locales/{en,ru}.json` and are read as `$t('section.key')`; lists (cases, FAQ…) come back as arrays.
- **Location comes from the config.** Copy says `{city}`, `{country}` and `{utc}`; they are filled from `src/lib/config/site-config.json` at build time (the UTC offset from its IANA time zone), in the page language, and the JSON-LD address uses the same file. Russian copy uses the names only in the nominative, so another city needs no grammar changes. `{years}` is computed from `works.en.json`.
- **Skills have one source.** `tree.json` (with `tree.ru.json` overlaying titles and descriptions by id) holds the skills; `CONSTELLATIONS` in `content.skill-tree.js` groups them (Agents, LLM & evals, Front-end, Back-end, Infrastructure) and `buildConstellations(lang)` returns the groups for the skill tree and the list. The page gets only the built list from its server load, not the whole tree: per skill its one-line summary, its `tier` (the group's lead, a main tool, or the rest — what the data holds, no invented levels), its links inside the group and the cases whose stack names it.
- **The skill tree** (`src/lib/sections/skill-tree/`), drawn as a star chart: the root («AI-native engineer») and one group at a time as a constellation, every skill a star with its name beside it. Tabs above the chart open a group (Agents first; without JavaScript every group's chart shows, one under another). Each group grows from its lead (the brightest star) in limbs — chains of stars, the main tools nearest the lead; a skill the data links to an earlier one (Vue → Nuxt, Python → FastAPI) follows it on the same limb, and nothing else about the lines claims anything. `constellation.js` lays out one chart per group for four layouts picked by the tree's own width (a container query): `n` (phones, two limbs) and `m` (tablets, three) hang the group down from the root on top; `w` (≥ 1000 px, up to seven limbs) and `x` (≥ 1320 px, up to nine) grow it up from the root at the bottom, over the Earth (the camera comes down to the horizon as the root scrolls into view). In the crown a group takes a limb per four or so of its skills (a crown of few limbs gets wider ones, centred), its limbs start at odd heights so they never line up into rows, and the lines to them run in low and turn up at the end; the root is a large star (120 px, a breathing halo, a second flare, a slow dotted orbit — none of it moving with reduced motion) with its name in 30 px under it. Type: names 14.5–17 px (`FONTS`), times 0.84 on phones and 0.94 on tablets. Positions are a fraction of the width across and px down; the lines are one stretched SVG per layout with non-scaling strokes. Heights come from the labels, wrapped at each layout's narrowest width with Manrope's measured glyph widths, so a wider screen only ever has more room. `node scripts/check-skill-chart.js <dev or preview origin, e.g. http://localhost:5173>` checks every group in both languages and every layout (labels that overlap, a line through a label, a label out of the tree or past its room); run it after changing the skills, the label fonts or the layout constants. All HTML, CSS and SVG: every name is in the prerendered page, readable without WebGL or JavaScript. Hover or focus shows a card and lights the path from the root; click, Enter or Space pins a panel with links to the cases (`#case-<id>` in Works; a sheet at the bottom on touch screens); one tab stop for the open chart, arrow keys move to the nearest star; a chart fades in as it scrolls into view, and again when its tab opens (not with reduced motion).
- **Scene contract** (`src/lib/scene/sceneStore.js`). `sceneStore` is a writable `{ section, progress }` (`hero | skills | process | works | offer | contact`, progress 0..1), always written with `update()`: `sceneProgress.js` writes it on scroll (the FAQ shares the `contact` stage) and mirrors the stage on `<html data-scene>`. The Skills section's view (tree or list) is the page's own business, remembered in `localStorage` as `skills-view-2`; the 3D sky draws no skill constellations of its own any more. `sceneStatus` goes the other way: the scene shell reports `pending | loading | live | poster` (WebGL is probed in a worker, since a first context costs 100–200 ms on the main thread; a yes from the worker is checked once on the page itself, a few ms, because Chrome's Disable3DAPIs policy, `--disable-webgl` and extensions that blank `getContext` leave workers their WebGL, and a renderer that fails to start would freeze every later Svelte update on the page).
- **The sky.** A dome with the base colour and a dim galactic band, the nebulae (domain-warped noise baked once into an equirectangular map when the scene starts — 4096×2048 on the high tier, 2048×1024 on the low one, 2 × 2 samples per texel, in strips over a few frames — then only sampled through a cubic B-spline, so the magnified map shows no texel facets; they drift slowly and part softly around readable content), a star field with halos on the brightest stars, and now and then a shooting star (at most one in 18–32 s, none with reduced motion; `?scene=debug` sends the first after 1.5 s).
- **Content in front of the scene.** Mark readable content with `data-scene-occlude` (cards, panels, text blocks, the header and footer). The scene dims its bright parts behind those boxes (a mask texture, so text never sits on a bright patch at any scroll position), hides its captions under them and never answers the pointer there; links and buttons stay clickable because the canvas never takes the pointer. `data-scene-keepout` marks the hero headline and lead: the whole-Earth shots frame the globe right of that text on wide screens and below it on phones (`earthFraming()` in `story.js`).
- **SEO.** Each language has its own title, description, canonical, hreflang (en, ru, x-default → `/en/`), Open Graph/Twitter image and one JSON-LD graph (Person, WebSite, WebPage, Service per format, FAQPage). `robots.txt` points to `sitemap.xml`. The canonical origin is `SITE_URL` in `src/lib/seo/site.js`.
- **No WebGL, reduced motion, no JS.** All text is in the HTML; the skill tree needs neither WebGL nor JavaScript (without JavaScript it is simply drawn, every group's chart one under another, with no tabs, cards or keyboard moves). Without WebGL (or with a software renderer, Save-Data, a weak device) the shell shows a poster of the hero instead of the canvas; a live scene that fails later (context lost, frames too slow even at the lowest pixel ratio, its code not loading) gives way to the same poster, and `data-scene-fail` on the shell says why. The poster is country-neutral (no home highlight, marker or arcs, a fixed view of the Earth): the shell draws the home marker over it as HTML from `site-config.json`, so changing the home needs no new poster. Re-run `scripts/scene-poster.js` only when the hero's look changes.
- **Share images.** `static/og/og-<lang>.jpg` carry no location either (name, hero line, job title, a neutral Earth): the box rebuilds the site without a browser, so they must survive a change of location. Re-run `scripts/og-image.js` after changing the name, the hero line or the job title.

## 3D model pipeline

The page uses no GLB model today (the old typing figure is gone); the pipeline stays for the next one. Create `static/models/` and put the file there first, the script stops if that folder is missing.

`pnpm model-pipeline:run` runs `scripts/model-pipeline.js`, which turns GLB/GLTF files into Threlte components:

1. It takes every `.glb` / `.gltf` in `static/models/` (skipping `*-transformed.*`).
2. For each one it runs `npx @threlte/gltf@2.0.3 <file> --root /models/ --printwidth 120 --precision 2` (needs network, because it fetches the CLI).
3. It moves the generated `<name>.svelte` into `src/lib/entities/3d/models/` and deletes it from `static/models/`. The `.glb` stays in `static/models/` because the component loads it from `/models/<name>.glb`.

Options (types, draco, texture transform and simplify, overwrite) are the `configuration` object at the top of the script; all are off by default. Existing components are skipped unless `overwrite` is on.

Checked 2026-11-05 on a one-triangle test GLTF outside the repo: `@threlte/gltf@2.0.3` writes a Svelte 4 component (`$$restProps`, slots), while `@threlte/gltf@latest` (3.x) writes Svelte 5 (`$props`, `{@render}`), so the script pins 2.0.3. One catch is left: the generated component imports `useGltf` from `@threlte/extras`, which is not a dependency now; add `@threlte/extras` at an exact `7.5.4` (the latest 7.x; 8.x is not for core 7) together with the first model. Tried 2026-11-05 in a copy of the repo outside it: `pnpm add -D @threlte/extras@7.5.4` next to core 7.3.2 gives no peer warnings, `check` and `build` pass, and the triangle's component mounted in the live scene (SwiftShader, `?scene=low`) loads `/models/tri.gltf` with no page or console errors; whether it is drawn where expected was not looked at.
